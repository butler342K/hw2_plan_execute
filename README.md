# ReAct-агент служби підтримки інтернет-магазину

## 1. Опис проєкту
ReAct-агент на LangGraph, який відповідає на запити клієнтів інтернет-магазину про статус замовлення, дату відправки та відстеження посилки (Нова Пошта / Укрпошта). Агент працює через OpenAI-сумісний LLM-провайдер (за замовчуванням `gpt-4.1` через зовнішній проксі, з підтримкою локальної Ollama `qwen3`). Ключові можливості: виклик tools для отримання реальних даних (без галюцинацій), захисні механізми (ліміт кроків, тайм-аут, детекція зациклення), повне логування траєкторії виконання у JSON та структурована фінальна відповідь (Pydantic).

## 2. Доменна задача
- **Домен:** e-commerce / служба підтримки клієнтів.
- **Що вирішує агент:** запити на кшталт «який статус мого замовлення У-0387776?», «коли відправили замовлення?», «де моя посилка за ТТН ...?».
- **Інструменти (tools):**
  - `search_order` — пошук замовлення в `data/orders.csv` за номером (У-/М-/К-) або телефоном клієнта, повертає статус і дату відправки.
  - `get_order_ship_date` — отримати лише дату відправки замовлення (без звернення до зовнішнього API — дані вже є в CSV).
  - `track_parcel` — відстеження посилки Нової Пошти за ТТН через офіційне API (`api.novaposhta.ua`).
  - `track_ukrposhta_parcel` — відстеження відправлення Укрпошти за ШКІ через офіційне API (`ukrposhta.ua`).

Кожен tool має Pydantic-схему аргументів із валідацією (мінімальна довжина запиту, допустимі префікси номера замовлення, мінімальна довжина ТТН/ШКІ), що відсікає некоректні виклики ще до звернення до даних чи API.

## 3. Архітектура
- **LLM-провайдер:** `ChatOpenAI` (OpenAI-сумісний ендпоінт, `OPENAI_BASE_URL`/`OPENAI_API_KEY`/`LLM_MODEL`) або `ChatOllama` для локального `localhost:11434` — вибір автоматичний за `OPENAI_BASE_URL`.
- **Граф (LangGraph `StateGraph`):**
  - `agent` — LLM вирішує, викликати tool чи завершити діалог; тут-таки перевіряються захисні механізми.
  - `tools` (`ToolNode`) — виконує tool calls, кожен виклик і результат логуються.
  - `respond` — перетворює фінальну текстову відповідь на структурований `SupportResponse` (`answer`, `order_number`, `tracking_number`, `status`, `resolved`) через `with_structured_output`.
  - Умовне ребро `agent → tools | respond`; `tools → agent` (цикл ReAct); `respond → END`.
- **Захисні механізми (`safety.py`, клас `RunGuard`):**
  - `max_steps = 10` — жорсткий ліміт кроків агента.
  - `timeout_seconds = 60` — тайм-аут виконання від старту запуску.
  - `LoopDetector` з `max_repeats = 3` — виявляє 3 поспіль однакові виклики одного tool з тими самими аргументами.
  - При спрацюванні будь-якого з них агент повертає часткову відповідь замість помилки.
- **Логування (`logger.py`, `TrajectoryLogger`):** кожен крок графа (`agent`, `tools`, `respond`, `agent_stopped`, `loop_detected`) записується з таймстемпом і часом від старту; повна траєкторія зберігається у `trajectory.json`.

## 4. Інструкція запуску
1. Клонувати репозиторій: `git clone <repo-url>`.
2. Перейти в директорію: `cd hw1_react_agent`.
3. Встановити залежності: `pip install -r requirements.txt`.
4. Налаштувати `.env` (див. `.env` у корені проєкту):
   - `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `LLM_MODEL` — доступ до LLM (або `http://localhost:11434/v1` для локальної Ollama).
   - `NOVA_POSHTA_API_KEY` — для `track_parcel`.
   - `UKRPOSHTA_API_TOKEN` — для `track_ukrposhta_parcel`.
5. Запустити агента на прикладовому запиті: `python agent.py` — виведе структуровану відповідь, кількість кроків і збереже `trajectory.json`.
6. Запустити тест-кейси: `python test_runner.py` (результати зберігаються у `test_results.json`).

## 5. Результати тестування
Підсумкова таблиця за `test_results.json` (реальний прогін `test_runner.py`):

| Test ID | Складність | Кроків | Tool calls | Час, мс | Статус |
|---------|------------|--------|------------------------------------|---------|--------|
| TC-001  | simple     | 2      | `search_order` × 1                 | 3009    | ✅ success |
| TC-002  | simple     | 2      | `get_order_ship_date` × 1          | 3492    | ✅ success |
| TC-003  | medium     | 2      | `track_parcel` × 1                 | 3928    | ⚠️ ТТН не знайдено в API Нової Пошти |
| TC-004  | complex    | 2      | `search_order` × 1, `track_parcel` × 1 | 4386 | ✅ success |
| TC-005  | edge-case  | 2      | `search_order` × 1                 | 2921    | ✅ success (коректна відмова) |
| TC-006  | complex    | 2      | `search_order` × 1                 | 3543    | ✅ success (ТТН не вигадано) |

Усі 6 кейсів завершились без помилок виконання (`status: success`) і зі структурованою відповіддю (`resolved: true`). У TC-003 сам агент відпрацював коректно — виклик `track_parcel` пройшов, але Нова Пошта не повернула даних за тестовим ТТН (стара база, ттн вже не відслідковується), тому агент чесно повідомив про відсутність результату, а не вигадав статус. TC-006 перевіряє ситуацію, коли клієнт дає лише номер замовлення (реальний ТТН цього замовлення є в `data/orders.csv`, але `search_order` його не повертає) — агент не підставив ТТН від себе, а відповів на основі доступних даних (статус замовлення), не викликавши `track_parcel` з вигаданим номером.

Приклад одного реального прогону (`trajectory.json`, запит «Який статус мого замовлення У-0387776 і коли його відправили?»): агент за 2 кроки паралельно викликав `search_order` і `get_order_ship_date`, отримав статус «доставлено» та дату відправки, і сформував фінальну відповідь — усього 6 подій траєкторії.

## 6. Аналіз результатів
**Чи правильно агент обирав tools?**
Так, у всіх 6 кейсах. Агент розрізняє близькі за змістом tools, а не бере перший-ліпший: у TC-001 («який статус?») викликав `search_order`, а в TC-002 («коли відправили?») — вужчий `get_order_ship_date`, хоча обидва запити стосуються того самого замовлення. У TC-004 він самостійно розпізнав, що потрібні дані з двох різних джерел (локальна база + зовнішнє API), і викликав `search_order` та `track_parcel` паралельно в одному кроці, а не послідовно.

**Де агент помилявся і чому?**
Явних галюцинацій не зафіксовано. Дві прикордонні ситуації варто відзначити:
- TC-005 (`Х-0000000`): Pydantic-валідатор `OrderSearchInput` відхилив виклик (`Номер замовлення має починатися з У-, М-, К-`), помилка інструменту повернулась агенту як `ToolMessage`, і той коректно переказав причину клієнту одним додатковим кроком — без ретраю й без спроби «вгадати» правильний номер.
- TC-006 (клієнт дав лише номер замовлення і спитав «де посилка»): агент відповів статусом замовлення, але не викликав `track_parcel` (правильно — ТТН йому не відомий) і **не запитав явно ТТН у клієнта**, хоча це очікувана поведінка. Це не галюцинація, але неповна взаємодія — місце для покращення системного промпту.

**Кроки: simple vs complex.**
У цьому наборі кількість кроків агента не залежить від складності — всі 6 кейсів (simple/medium/complex/edge-case) завершились рівно за 2 кроки. Причина: LangGraph/LLM підтримує паралельні tool calls в межах одного кроку (TC-004 викликав 2 tools за 1 крок агента), тому складність запиту проявляється не в кількості кроків ReAct-циклу, а в кількості tool calls усередині кроку.

**Чи досягав агент max_steps або timeout?**
Ні. Максимум використаних кроків — 2 з 10 (`max_steps`), тобто 20% ліміту. Час виконання — 2.9–4.4 с з тайм-аутом 60 с, тобто до 8% ліміту. Запас великий; `LoopDetector` (max_repeats=3) також жодного разу не спрацював.

**Залежність часу виконання від складності.**
Помітна, хоч і невелика: найшвидший кейс — TC-005 edge-case (2921 мс, лише локальна CSV-валідація), найповільніший — TC-004 complex (4386 мс, 2 tool calls, з них один — мережевий виклик Nova Poshta API). Кейси з одним зовнішнім API-викликом (TC-003, TC-006) middle-range (~3.5–3.9 с). Тобто основний внесок у latency дає не сам LLM-крок, а кількість і тип tool calls (мережеві API повільніші за читання CSV).

**Випадки, коли агент НЕ використав tool, хоч мав би.**
Не зафіксовано — у кожному з 6 кейсів агент викликав хоча б один tool перед фінальною відповіддю, що узгоджується з системним промптом («ніколи не вигадуй... якого немає в результаті виклику tool»). Найближчий прикордонний випадок — TC-006 вище, де tool для частини запиту («де посилка») не було викликано через відсутність вхідних даних (ТТН), а не через пропуск з боку агента.

## 7. Висновки та обмеження
- Що працює добре: точний вибір між близькими tools (`search_order` vs `get_order_ship_date`), паралельні tool calls у складних запитах, коректна відмова без галюцинацій при невалідному номері замовлення чи ненайденому ТТН, структурована фінальна відповідь, захист від зациклення й перевищення лімітів.
- Що можна покращити: якщо дата доставки в минулому, а ТТН немає - потрібна обробка затримки відправки.
- Відомі обмеження: `track_parcel`/`track_ukrposhta_parcel` залежать від доступності зовнішніх API Нової Пошти/Укрпошти.

## 8. Структура файлів
- `tools.py` — Pydantic-схеми та tools (`search_order`, `get_order_ship_date`, `track_parcel`, `track_ukrposhta_parcel`)
- `agent.py` — LangGraph граф (`agent` → `tools`/`respond`), структурована відповідь `SupportResponse`
- `safety.py` — `RunGuard`: max_steps, timeout, `LoopDetector`
- `logger.py` — `TrajectoryLogger`
- `test_runner.py` — тест-кейси
- `data/orders.csv` — база замовлень
- `trajectory.json` — лог траєкторії (генерується)
- `test_results.json` — результати тестів (генерується)
